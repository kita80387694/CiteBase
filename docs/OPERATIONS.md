# 本地运行与故障处理

本手册对应第三阶段源码。双进程与负载结果以 `docs/results/quality-phase3/operations/` 中实际终态报告为准；RUNNING/FAILED 报告不能作为整套验收通过。模型质量和真人评审不属于健康检查的证明范围。

## 启动、健康和监控

使用 README 的 Compose 启动方式，保留已有 `.env` 和数据库卷。容器 readiness 检查 `/actuator/health/readiness`，包含真实数据库连接和查询；`/actuator/health/liveness` 只检查进程状态。连接获取和查询均有界，不用模型调用探活，不把供应商余额或回答质量等同于健康状态。

登录后进入“运行状态”。`/api/operations/summary?windowMinutes=60` 在 SQL 聚合前绑定认证用户，只展示本人的任务与调用，统计跨 worker 共享数据库；窗口允许 5–1440 分钟。积压和最老等待是当前状态，耗时包括排队和重试等待；无样本显示不可用。调用的 STARTED 是仍等待返回的记录数量，不是历史调用总量；同步基础问答不进入持久任务账本。V10 事件不伪造历史回填。完整口径见 `API-CONTRACT-OPERATIONS.md`。

可选设置至少 32 字符随机 `OPERATIONS_TOKEN`，通过请求头 `X-Operations-Token` 访问 `/api/operations/local`。该令牌只供本机运维客户端使用，不能写入前端、截图、提交、日志或报告。未设置或错误返回 404。返回本 JVM 的堆、CPU、连接池和低基数任务指标，**不是全数据库或集群聚合**。普通用户登录不赋予此权限。Compose 端口绑定回环地址，不公开部署。

## 告警解释

- 积压持续增长或最老等待增加：先检查 worker 是否开启、活跃数与并发上限、数据库 readiness、供应商延迟。HTTP 202 只代表已持久化，不代表完成。
- 租约回收：检查旧 worker 是否崩溃、长时间暂停或数据库不可用；不要手工把所有 RUNNING 改为 QUEUED。领取和发布使用代次校验，晚到旧结果不能覆盖新结果。
- UNKNOWN 调用：供应商可能已执行但本地未保存。不能按零成本处理，也不能保证 exactly-once；先查任务详情及原调用账本，再决定有限重试。
- 429 / PROVIDER_TIMEOUT：检查实际重试次数、退避和队列。不要把全部失败任务无条件批量重提；额度/认证错误需要外部修复。
- UNSAFE_TO_RESUME：Agent 在执行中断后缺少安全续跑条件，保留失败与未知调用。用户如需重新执行，应明确新建运行并接受再次调用的可能成本。
- FENCE_REJECTED：旧 worker 试图写入已失效的执行代次。计数属于实例失败尝试，事务回滚，不能当作 SELF 持久事件条数。

数据库领取失败至少退避 5 秒，日志全实例每 30 秒最多一条警告；指标仍累计失败尝试。任务并发上限是每 JVM 的约束，不是全局供应商预算。同步问答负载与异步任务负载需要分别测量。

## 取消、恢复与缓存

任务页可取消、查看失败和部分结果、按允许语义重试。取消后不调度新步骤；在途 HTTP 可能继续在供应商执行，但晚到结果不恢复为成功。评测按已保存项目检查点恢复，不重复已完成项目。索引失败保留旧活动版本。

检索缓存默认关闭，进程内有容量、字节和 TTL 上限。每次命中仍重新验证权限与来源版本。重启会清空缓存；不能把重启前后请求当作同一连续热缓存测量。文档删除、版本切换和知识库访问变化按服务端规则撤回；不要通过延长 TTL 绕过这些检查。

## 备份与升级

升级前备份目标项目数据库，用明确容器名执行 `pg_dump`，并将备份放在仓库外的受限位置。可使用 `docker exec <db-container> pg_dump -U citebase -d citebase -Fc -f /tmp/citebase.backup` 后 `docker cp` 到明确目标；不要把二进制备份经过旧 PowerShell 文本重定向。备份可能包含完整文档、密码哈希和评审依据，不得提交。

恢复演练必须创建独立数据库/卷，核对文件完整性后再使用 `pg_restore`；不要对正在使用的数据执行清库恢复。应用 Flyway 历史迁移校验不可修改。V10 新建任务事件表，不回填历史，删除任务会级联撤回事件。旧 V5 worker 不具备 fencing，升级时先停止它们，不能混跑。保留数据库卷，禁止用 `down -v` 掩盖迁移问题。

真实基线和探索环境是冻结实验运行时。不要在这些项目上随意执行 `up --build`；新代码实验用新的项目、端口、卷与注册记录。真人评审所需资料保持可访问，当前尚无真人评分。

## 已观测结果与部署限制（2026-10-01）

本轮两个实际JVM与专用PostgreSQL运行已完成13项检查，原始终态 PASSED：`results/quality-phase3/operations/two-process-1790834245097/report.json`；派生统计为 [运维工程报告](results/quality-phase3/operations-engineering-report.json)。794条测量操作无失败，并发1/2/4/8的观察吞吐分别1.669/3.509/4.969/5.066操作每秒，端到端P95分别1053/993/1545/2904 ms。并发4/8达到240操作上限，窗口只有48.304/47.379秒，不是完整60秒持续测量。详细资源与排队表见 [负载说明](LOAD_TESTING.md)。

数据库暂停8秒后的199 ms恢复观测，定义为unpause返回到释放在途门控并验证任务完成，不是故障总时长或生产SLO。两个JVM的active task采样最大值均为1，数据库连接最大观察值13（含观察连接）；这仅是采样，不构成所有瞬间严格上限证明。两次前置失败尝试完整留存，没有覆盖原始FAILED报告。

当前没有全局API admission限流、全局入队上限或集群供应商配额控制。每worker的semaphore约束异步任务执行，同步基础RAG不经过该semaphore。队列在开放环长期过载时仍可能增长；不能把本次闭环、固定mock延迟下的零失败解释为生产背压和过载保护已经完备。部署前应依据实际到达率与供应商约束设置外部入口限流及容量策略，并重新验证，不以本次测试替代。

所有模型步骤为明确mock/fault适配器，结果只证明该环境中的工程行为。真实模型质量、成本非劣及真人评审门槛仍独立存在；目前真人评审未完成，不宣称第三阶段全部验收通过。
